## Prerequisites

- Discovery context from Step 1

## Overview

Step 1.7 analyzed the codebase and produced structured JSON artifacts. This step transforms those artifacts into human-readable, frontmatter-rich documentation that agents consume during `/plan_w_team` and `/build`.

**Produces:**
- `docs/modules/<module>.md` — one doc per module, with YAML frontmatter
- Populated `docs/ARCHITECTURE.md` — real content from analysis (only if empty or stub)
- Populated `docs/DEVELOPMENT.md` — real content from analysis (only if empty or stub)
- `docs/modules/ROUTING.md` — module routing table (owned exclusively by `/document`)
- Updated `docs/README.md` with modules index

**Preservation rule:** Existing human-written content is never overwritten. Sections marked with `<!-- human-maintained -->` are preserved during updates. Files with substantial existing content (>50 lines of non-boilerplate) are not overwritten — only missing sections are appended.

## YAML Frontmatter Schema

Every module doc starts with YAML frontmatter that agents and tools parse:

```yaml
---
module: auth                          # kebab-case identifier, matches modules.json
title: "Authentication & Session Management"
type: module                          # module | service | data-model | integration

# === Agent Routing ===
source_paths:                         # files this doc describes (for staleness detection)
  - src/middleware/auth.ts
  - src/services/AuthService.ts
read_when:                            # broader globs — when to consult this doc
  - src/middleware/auth*
  - src/services/Auth*
  - src/routes/auth*

# === Dependencies ===
depends_on: [database, api-routing]
depended_by: [task-management]

# === Staleness Detection ===
last_analyzed:
  commit: "a1b2c3d"
  date: "2025-03-15"

# === Confidence ===
confidence: high                      # high | medium | low
open_questions:
  - "Is refresh token rotation intentional or a TODO?"

generated_by: discovery               # discovery | human | hybrid
tags: [security, middleware, jwt]
---
```

**Key fields:**
- `source_paths` — exact files this doc describes. Used for staleness: count commits to these files since `last_analyzed.commit`.
- `read_when` — broader globs. Used for agent routing: when an agent is about to modify files matching these patterns, it should read this doc first.
- `confidence` — how confident the discovery agent was in its analysis. `high` = clear patterns, user-confirmed. `medium` = reasonable inference. `low` = guesswork, needs human review.
- `generated_by` — `discovery` (generated by this step), `human` (written by a person), `hybrid` (generated then edited by a person).

## Generation Process

### 1. Read Discovery Artifacts

Load from `{{agent_dir}}/discovery/`:
- `context.json` — global architecture, patterns, conventions
- `modules.json` — module definitions with source paths and dependencies
- `questions.json` — questions and answers

### 2. Create Module Directory

```bash
mkdir -p docs/modules/
```

### 3. Generate Per-Module Docs

For each module in `modules.json`:

1. **Check for existing doc:** If `docs/modules/<module>.md` already exists:
   - Parse its YAML frontmatter
   - If `generated_by: human` or `generated_by: hybrid`, do NOT overwrite
   - If `generated_by: discovery`, update in place (preserve `<!-- human-maintained -->` sections)

2. **Build frontmatter** from `modules.json` data:
   - `module`, `title`, `type` from the module entry
   - `source_paths`, `read_when` from the module entry
   - `depends_on`, `depended_by` from the module entry
   - `last_analyzed.commit` and `last_analyzed.date` from the analysis timestamp
   - `confidence` from the module's confidence rating
   - `open_questions` from unanswered questions in `questions.json` where `question.module == module.name`. Filter explicitly by the `module` field — do not include questions from other modules. Skip any question missing a `module` field and emit a warning: "Question <id> has no module field — skipped."
   - `generated_by: discovery`
   - `tags` derived from module type, framework, and patterns

3. **Build body** using the template above:
   - **Overview** — synthesize from module analysis in `context.json`
   - **Key Files** — from `source_paths`, add responsibility descriptions from Phase B analysis
   - **Data Flow** — from the module's `data_flow` field in `modules.json`
   - **Patterns & Conventions** — from the module's `key_patterns` and global `conventions`
   - **Dependencies** — from `depends_on` (internal) and package imports (external)
   - **Testing Notes** — from test file analysis in Phase B
   - **Open Questions** — from unanswered questions in `questions.json` where `question.module == module.name` (filter by `module` field; skip questions with null/missing `module` with a warning)

### 4. Populate Permanent Docs (If Stub)

**`docs/ARCHITECTURE.md`** — If the file is empty or contains only a header/placeholder:
- Write the architecture style and description from `context.json`
- Include the module dependency diagram
- Document the data model overview
- List entry points and their roles

**`docs/DEVELOPMENT.md`** — If the file is empty or contains only a header/placeholder:
- Document the patterns and conventions from `context.json`
- Include the testing approach
- Document the module structure for navigation

If a file exists and is not empty (has any non-whitespace content beyond a title header), leave it unchanged — do not overwrite existing content regardless of line count. Only populate files that are completely empty or contain only a title line.

### 5. Generate `docs/modules/ROUTING.md`

Write the routing table to `docs/modules/ROUTING.md`. This file is owned exclusively by `/document` and is overwritten on every run — it is never human-edited.

`/document` is also responsible for ensuring `CLAUDE.md` (or `AGENTS.md` on OpenCode) contains the reference line. Check whether the line already exists; if not, append it to the Module Documentation section (or add the section if absent):

```
See `docs/modules/ROUTING.md` for the module routing table.
```

Do not add duplicate lines. Do not overwrite other CLAUDE.md content — locate and update only the Module Documentation section.

**Format of `docs/modules/ROUTING.md`:**

```markdown
# Module Routing Table

> Generated by `/document --update-routing`. Do not edit manually.

When modifying code, consult the relevant module doc before making changes.

| File pattern | Module doc | When to consult |
|---|---|---|
| `src/auth/**` | [Authentication](auth.md) | Auth logic, JWT, session handling |
| `src/database/**` | [Database](database.md) | Queries, migrations, repository pattern |
```

**Routing table rules:**
- Maximum ~20 rows — if more modules exist, group related ones
- Each row maps a file-pattern glob to the module doc and a short "when to consult" note
- No prose in the table — just patterns, paths, and notes
- The file is always regenerated from current `modules.json` data; do not add manual rows

### 6. Update `docs/README.md`

Add a "Module Documentation" section to the docs index:

```markdown
## Module Documentation

Detailed module-level documentation generated from codebase analysis.

| Module | Description | Doc |
|--------|-------------|-----|
{{#each modules}}
| {{title}} | <1-line description> | `docs/modules/{{name}}.md` |
{{/each}}

Run `/discovery` to refresh module analysis. Run `/document` to regenerate docs.
```

### 7. Update the "When to Update" Table

Add a row to the existing "When to Update" table in `docs/README.md`:

```markdown
| Changed implementation within a module | `docs/modules/<module>.md` |
```

## Updating Existing Module Docs

When `/document --module <name>` or `/document --all` runs on a project with existing module docs:

### Preservation Rules

1. **Never overwrite `generated_by: human`** — These were written by a person. Skip entirely.

2. **`generated_by: hybrid`** — Update frontmatter only (`source_paths`, `read_when`, `depends_on`, `depended_by`, `last_analyzed`, `confidence`, `open_questions`); preserve the entire body verbatim. Treat the body as human-authored.

3. **Preserve `<!-- human-maintained -->` sections** — During update, scan for this marker. Everything between `<!-- human-maintained -->` and the required closing `<!-- /human-maintained -->` tag is preserved verbatim. The closing tag is required. If an opening `<!-- human-maintained -->` tag is found without a corresponding closing `<!-- /human-maintained -->` tag, emit a warning in the command output and treat the boundary as ending at the next section header (as a recovery fallback). Do not silently discard content.

   **When to use each protection mechanism:**
   - Use `<!-- human-maintained -->` / `<!-- /human-maintained -->` tags to protect a specific section within a `generated_by: discovery` doc. The surrounding sections will still be regenerated; only the tagged block is preserved.
   - Use `generated_by: hybrid` in the YAML frontmatter to protect the ENTIRE document body from regeneration (only frontmatter fields are updated). Use this when you have written substantial content across the whole document and want full body protection.
   - Do NOT set `generated_by: hybrid` manually without understanding that this freezes the entire body. There is no `/document` command to set this flag — edit the frontmatter directly and be intentional.

   **Orphaned blocks during major drift:** During `/discovery --module <name>`, if a module's staleness is `major_drift`, the command output should list any `<!-- human-maintained -->` sections in that module's doc and prompt the user to verify their accuracy. This is a reminder only — human-maintained sections are never auto-removed.

4. **Update frontmatter** — Always update `source_paths`, `read_when`, `depends_on`, `depended_by`, `last_analyzed`, `confidence`, and `open_questions` from fresh discovery data.

5. **Merge, don't replace** — For `generated_by: discovery` docs:
   - Update sections with new analysis data
   - Preserve any manually added sections
   - Update the "Key Files" table if files were added/removed
   - Update "Dependencies" if imports changed

### Staleness-Triggered Updates

When `/document --all` runs:
1. For each module doc, check commits to `source_paths` since `last_analyzed.commit`
2. If 0 commits: skip (still fresh)
3. If 1-5 commits: update frontmatter only (minor drift)
4. If 6+ commits: full regeneration of body content (with preservation rules)

## `--update-routing` Mode

When running `/document --update-routing`:

Only regenerate `docs/modules/ROUTING.md` and the `docs/README.md` module index from current `modules.json` data. Do not touch any module docs. This is useful after manually adding or removing module docs.
