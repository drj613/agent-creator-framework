## Documentation Directory

If `{{discovery.existing_docs.has_docs_dir}}` is false, create the full structure:

```
docs/
├── README.md          # Master index — "When to Update" table linking changes → docs
├── ARCHITECTURE.md    # System design, data flow, services
├── DEVELOPMENT.md     # Local setup, dev commands, testing
├── DEPLOYMENT.md      # Production deploy procedures
├── DECISIONS.md       # Architecture Decision Records (ADRs)
├── PERFORMANCE.md     # Bottlenecks, optimizations, benchmarks
└── modules/           # Per-module docs from /discovery + /document (deep_discovery feature)
    ├── ROUTING.md     # Generated routing table — do not edit manually
    └── <module>.md    # Module doc with YAML frontmatter
CHANGELOG.md           # Version history — updated on every commit (project root)
```

The `docs/modules/` directory is only created when `{{discovery.features.deep_discovery}}` is true. Module docs are generated by the `/document` command from discovery analysis artifacts.

If `CHANGELOG.md` does not exist at the project root, create it with a minimal header:

```markdown
# Changelog

All notable changes to this project will be documented in this file.
```

If docs already exist (`{{discovery.existing_docs.has_docs_dir}}` is true), check which files are present and only create missing ones. Do NOT overwrite existing docs.

### `docs/README.md` — The "When to Update" Table

This table is what makes the rules self-service. Every developer (human or agent) checks it to know where changes should be documented.

```markdown
# Documentation Index

## When to Update

| You changed... | Update this file |
|----------------|-----------------|
| System architecture | `docs/ARCHITECTURE.md` |
| Local dev setup | `docs/DEVELOPMENT.md` |
| Deploy process | `docs/DEPLOYMENT.md` |
| Made an architectural decision | `docs/DECISIONS.md` |
| Found/fixed a performance issue | `docs/PERFORMANCE.md` |
{{#if discovery.features.deep_discovery}}
| Changed implementation within a module | `docs/modules/<module>.md` (and run `/document --update-routing` if module names changed) |
{{/if}}
| Any code change at all | `CHANGELOG.md` |

## Permanent Documents

These files are updated in place — never create a new file when one of these covers the topic:

- **ARCHITECTURE.md** — system design, data flow, services
- **DEVELOPMENT.md** — local setup, dev commands, testing
- **DEPLOYMENT.md** — production deploy procedures
- **DECISIONS.md** — architecture decision records (ADRs)
- **PERFORMANCE.md** — bottlenecks, optimizations, benchmarks

## Temporary Documents

Temporary docs (analysis summaries, meeting notes, versioned guides) should be cleaned up
after their insights are extracted into permanent docs. Run `/audit-docs` to identify stale
temporary files.

{{#if discovery.features.deep_discovery}}
## Module Documentation

Detailed module-level documentation generated from codebase analysis. See `docs/modules/ROUTING.md` for the full routing table.

Run `/discovery` to refresh module analysis. Run `/document` to regenerate docs.
{{/if}}
```

## Doc Auditing — Background and Heuristics

Left unmanaged, a `docs/` folder accumulates fast: meeting summaries, versioned deployment guides, one-off analysis files, duplicate setup docs. The documentation rules (Step 6) prevent new sprawl, but they don't catch drift — permanent docs going stale as the codebase moves on without them.

The `/audit-docs` command (defined in Step 3) invokes the `audit-docs.sh` shell script (defined in Step 5) to collect all deterministic signals — git history, file metadata, pattern matching, risk scoring — and produce structured JSON. The LLM then interprets the JSON output to add judgment. This section explains the heuristics the script uses and when to run the command.

### When to Run `/audit-docs`

The `audit-docs-hook.sh` (Step 5) handles commit-time checks automatically — it flags temporary files by filename pattern on every `git commit` without any manual step. That covers the common case.

Manual `/audit-docs` runs are for deeper sweeps:

- **After a sprint / milestone** — full co-change analysis to catch permanent docs drifting from the code they describe
- **Monthly with `--fix`** — auto-clean obvious cases that have accumulated
- **Before a major refactor** — identify which permanent docs will be invalidated by the upcoming work, so they can be updated as part of the plan rather than after

The audit command can also be added as the final task in any `/plan_w_team` that involves significant architectural changes — the plan's validation step runs the audit to confirm docs were kept in sync.

### Staleness Heuristic: Co-Change Analysis

The most useful signal is co-change: if `ARCHITECTURE.md` was last updated in the same commit that added a particular module, but that module has since been rewritten across 20 commits, the doc is almost certainly stale even if it's not obviously "temporary."

```bash
# Find source files that changed frequently since a doc was last updated
LAST_DOC_COMMIT=$(git log -1 --format="%H" -- docs/ARCHITECTURE.md)
git log $LAST_DOC_COMMIT..HEAD --name-only --pretty=format: | sort | uniq -c | sort -rn | head -20
```

Include this output in the audit report for any permanent doc that hasn't been touched in > 45 days. Files with high churn since the doc's last edit are the ones most likely to have diverged from what the doc describes.

## Specs Audit

In addition to `docs/`, the `specs/` directory accumulates plan files from `/plan_w_team`. Over time, many become stale. The `/audit-docs` command should also audit `specs/`.

### For Each File in `specs/`

**1. Check if built:**
- Search git log for commits referencing the spec filename
- Check if the spec's listed files in "New Files" or "Relevant Files" exist and were modified after the spec was created

**2. Check age:**
- Specs older than 30 days that show no evidence of being built are likely abandoned

**3. Classify:**

| Status | Criteria | Action |
|--------|----------|--------|
| **Built & Complete** | All acceptance criteria appear met, files exist, tests pass | Archive (move to `specs/archive/`) or delete |
| **Built & Partial** | Some files created but acceptance criteria not fully met | Flag for user review |
| **Never Built (old)** | > 30 days, no git evidence of implementation | Flag as abandoned, recommend delete |
| **Never Built (recent)** | < 30 days, no git evidence yet | Leave alone |

### Report Format Addition

When running `/audit-docs`, include a specs section in the output:

```
### Specs Status
- `specs/add-user-auth.md` — Built & Complete (15 commits reference it). Recommend: archive.
- `specs/migrate-database.md` — Never Built, 45 days old. Recommend: delete or implement.
- `specs/fix-login-flow.md` — Built & Partial (3 of 5 acceptance criteria met). Needs review.
- `specs/add-dark-mode.md` — Never Built, 5 days old. Leave.
```
